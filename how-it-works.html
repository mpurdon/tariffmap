Methodology

How the tariff data is updated

Every measure on the map lives in one hand-curated JSON file in a public repository. A scheduled AI agent checks the primary sources every week and proposes changes as pull requests; a person reviews and merges them; merging rebuilds and redeploys the site. Trade values are refreshed separately from official statistics. This page documents each step exactly.

The weekly cycle

  1. Mon 06:00 UTCTrade data refresh. A scheduled build re-queries UN Comtrade, Statistics Canada and the US Census, commits the refreshed caches and redeploys.
  2. Mon 12:00 UTCSource check. The curation agent sweeps the primary sources for anything that started, ended, changed rate or was formally announced since the last check.
  3. Same runTwo outputs. Measure changes go into a pull request for review. Separately, the run records that the check happened, even when nothing changed.
  4. When reviewedHuman merge. The maintainer reviews each proposed change against its cited source and merges, edits or rejects it.
  5. ~1 minute laterDeploy. Every push to main validates the dataset, rebuilds and deploys. Browsers pick up new data within the hour.

1 · The dataset

The single source of truth is data/curated/tariff-actions.json. Nothing reaches the map unless it is in this file. Each entry is one legal instrument (split by target group when the rate differs), for example: 

{
  "id": "us-232-steel-alu-2025",
  "imposer": "USA",                 // ISO3; EUN = European Union
  "targets": ["ALL"],               // or a list of ISO3 codes
  "except": ["GBR"],                // carve-outs covered by their own entry
  "rate": 50,                       // headline ad valorem %, or null for bans
  "rateHistory": [{"from": "2025-03-12", "rate": 25},
                  {"from": "2025-06-04", "rate": 50}],
  "stacksWith": ["…"],              // measures whose rates add on the same goods
  "hs": ["72", "73", "76"],         // HS chapters/headings covered, or ["ALL"]
  "legalBasis": "Section 232",
  "effective": "2025-03-12",        // date the duty became payable
  "expires": null,
  "status": "active",               // active | suspended | revoked | announced
  "sources": ["https://www.federalregister.gov/…"],
  "lastVerified": "2026-09-13"
}

Rules the file follows:

  • Every entry cites at least one source, preferably the legal instrument itself: Federal Register proclamations, USTR notices, CBP CSMS messages, Finance Canada orders, the EU Official Journal, MOFCOM / State Council Tariff Commission announcements, Mexico's Diario Oficial.
  • History is never deleted. An ended measure gets an expires date and status: "revoked"; a rate change is appended to rateHistory. That is what lets the timeline replay any past month.
  • Dates are when the duty became payable, not when the order was signed.
  • Bans and non-ad-valorem measures have rate: null, with the detail in rateNote; bans are drawn with their own red, strobing style.

Every build runs a validator and refuses to deploy if any entry has an unknown country code, no sources, a rate outside 0–250%, a malformed date, a revoked status without an end date, a rateHistory that disagrees with rate or effective, a duplicate id, or a stacksWith pointing at a measure that does not exist.

2 · The weekly source check

The check is run by an AI agent (Anthropic's Claude) as a scheduled cloud job. It starts from a fresh clone of the repository and follows the written procedure in docs/CURATION.md, which you can read in full. In outline:

  1. Establish the window. It reads the date of the previous completed check and the newest lastVerified in the dataset, and looks for developments since then.
  2. Sweep the sources in a fixed order: Federal Register (presidential proclamations, USTR and Commerce notices), USTR press releases, CBP CSMS messages, Finance Canada, European Commission trade news, MOFCOM / Tariff Commission, Mexico's Diario Oficial. Global Trade Alert and established trade-law trackers are used only to cross-check dates and carve-outs, never as the sole source.
  3. Re-verify anything due. Every entry with an effective date, expiry or scheduled rate change within ±14 days of the run is checked again to confirm it actually happened or was postponed.
  4. Edit within strict limits. The agent may change only the dataset file (and the country list, if a new trading partner appears). Each new or changed entry must cite a primary source and gets today's lastVerified. It may not touch code, workflows, build output or caches.
  5. Validate. It runs the same build and validator as production, offline, and must get zero errors.

Scope is deliberate: tariffs, surtaxes, anti-dumping and countervailing duties, safeguard quotas with an over-quota rate, import bans, and formal suspensions or terminations of any of these, imposed by or on a mapped economy. Export controls, sanctions and entity lists are out of scope, as are proposals that have no legal instrument or effective date yet. The guiding rule is that an omission is recoverable; a wrong rate on the live map is not.

3 · What a run produces

Proposed changes → pull request

If any entry changed, the agent commits only the dataset to a curation/YYYY-MM-DD branch and opens a pull request. Its description has one row per change (measure, change, effective date, source link, and the agent's confidence), plus developments it saw and chose not to record, with reasons. These are never committed to the live site directly.

See every curation pull request →

The check itself → last-check.json

Every completed run, changes or not, writes data/curated/last-check.json (the date, the outcome, the pull request if any, and how many entries it re-verified) and commits that one file straight to main. It changes no measure; it is what moves the “Sources checked” date in the map's header.

A run only counts as completed if the agent could read the primary sources directly. If they were unreachable, it records nothing and reports which sites failed. The header's dot turns amber with “check overdue” when the last completed check is more than nine days old, so a broken or skipped run is visible on the site rather than hidden behind a stale date.

4 · Human review and deploy

The maintainer reviews every curation pull request against its cited sources before merging. An agent-proposed rate, date or scope reaches the public map only through that merge.

Every push to main, whether a merged review, a check record or a code change, runs a GitHub Actions workflow:

npm ci                          # exact, locked dependencies
npm run typecheck               # TypeScript, no emit
npm run build:data -- --offline # validate + derive arcs from committed caches
npx vite build                  # bundle the site
npx wrangler deploy             # publish to Cloudflare

The site is static files on Cloudflare's edge: there is no server or database behind it. The data files are cached for at most an hour, so a merged change is visible to everyone within about an hour of deploy.

5 · How the numbers on the map are computed

Who is taxing whom, on a given date

  • Targets. ["ALL"] expands to every mapped economy except the imposer and any listed carve-outs. EU member states trade as one entity, so they collapse into the European Union.
  • In force. A measure applies on a date if it has taken effect, has not expired, and is not suspended. Its rate on that date is the latest rateHistory step on or before it.
  • Headline rate per arc. All measures between one imposer and one target are combined. Each measure is added to the measures it explicitly stacks with, and the largest stack wins. If any economy-wide measure applies, the headline is the economy-wide stack, with product-specific peaks shown separately as “up to X% on some products”.
  • Timeline. Years from the first measure up to two years ago, then months up to now, then one step per scheduled future change. Playback stops at “Now”.

How much trade is affected

  • Country level: UN Comtrade. Annual goods imports, HS classification, as reported by the importing country in US dollars, for the most recent year with data (2025, else 2024, else 2023). The build queries each imposer's imports from all its partners for every HS code its measures cover, chunked to stay under the API's row limit, spaced and retried on errors, and caches every response.
  • Covered value. For each arc, the imports under the HS codes the active measures cover. A heading inside a listed chapter is not double-counted, and an economy-wide measure covers total imports. Where a government publishes its own figure (for example, “C$27.6B of US goods”), that official figure is used instead.
  • Duty figure. Covered imports × rate. This is a ceiling: it ignores exemptions, quotas and the trade the tariff itself diverts. It is not a revenue estimate.
  • Regional view (zoomed in on North America): Canadian provinces use Statistics Canada table 12-10-0175-01, provincial domestic exports by product section, summed over the trailing 12 months and converted at an approximate C$0.73 per US$. US states use the Census Bureau's annual state exports by HS code. HS codes are mapped onto Statistics Canada's product sections approximately, and regions with under US$25M of exposed exports are left off to keep the map readable.

6 · Known limitations

  • Trade statistics lag by a year or more, so covered values describe the pre-tariff baseline, not current flows.
  • Headline rates simplify. Tiers, quotas and exemptions are in each entry's details, but the arc shows a single number.
  • The weekly check can miss things or misread them. That is why it proposes rather than publishes, and why every entry links to the document it rests on.
  • Between a policy change and the next completed check, the map can be up to a week behind.

Spotted an error? Open an issue with a link to the source document.
